Lab 02: Register Apps in Microsoft Entra ID

Create the two app registrations the code labs use: a public client that signs users in, and a confidential daemon that runs without a user.

Microsoft Entra admin centerBeginner~12 min

Scenario and Objectives

Your team is building a console tool that shows the signed-in user's colleagues, and a nightly job that reports on all users. Each needs its own identity with only the access it requires.

  • Register a single-tenant public client for delegated access with device code sign-in.
  • Register a single-tenant confidential client for app-only access.
  • Add least-privilege delegated and application permissions, and grant admin consent.
  • Create a short-lived client secret and keep it out of source control.
Related topic: Authentication and Permissions · Security Best Practices

Prerequisites and Names

  • A test or developer tenant in Microsoft Entra ID.
  • An account that can register apps (at least Application Developer) and grant admin consent to application permissions (Privileged Role Administrator or Global Administrator). In a developer sandbox, use the admin account.
  • A short <suffix> to keep names unique, such as your initials.
  • A safe place to keep the values you record, such as a password manager or a local text file outside any Git repository.

Build

Step 1: Open App Registrations

  1. Sign in to the Microsoft Entra admin center with your test-tenant admin account.
  2. If you have access to several tenants, use the Settings icon in the top menu to switch to your test tenant.
  3. Browse to Entra ID > App registrations.

Step 2: Register the Public Client

  1. Select New registration.
  2. Enter the Name graph-workshop-user-<suffix>.
  3. Under Supported account types, select the single-tenant option, Single tenant only - <your tenant>.
  4. Leave Redirect URI empty and select Register.
  5. On the Overview page, record the Application (client) ID and the Directory (tenant) ID.
Note: Some tenants still show the older label Accounts in this organizational directory only for the single-tenant option.

Step 3: Allow Device Code Sign-In

  1. Under Manage, select Authentication.
  2. Find Allow public client flows (under Advanced settings) and set it to Yes.
  3. Select Save.
Note: Device code flow is a public client flow, so this setting is required for Lab 04. Leave it off for apps that don't need it.

Step 4: Add Delegated Permissions

  1. Under Manage, select API permissions. User.Read is already listed.
  2. Select Add a permission > Microsoft Graph > Delegated permissions.
  3. Search for and select User.ReadBasic.All, then select Add permissions.

Expected result: Configured permissions lists User.Read and User.ReadBasic.All, both of type Delegated. Users can consent to both themselves, so admin consent is optional here.

Step 5: Register the Confidential Client

  1. Return to App registrations and select New registration.
  2. Enter the Name graph-workshop-daemon-<suffix>, choose the single-tenant option, leave Redirect URI empty, and select Register.
  3. Record this app's Application (client) ID. The tenant ID is the same as before.

Step 6: Add an Application Permission and Grant Admin Consent

  1. Select API permissions. In the User.Read row, select the ellipsis (...) > Remove permission > Yes, remove. The daemon never signs a user in, so it doesn't need it.
  2. Select Add a permission > Microsoft Graph > Application permissions.
  3. Search for and select User.Read.All, then select Add permissions.
  4. Select Grant admin consent for <your tenant>, then Yes.

Expected result: The User.Read.All row shows type Application and status Granted for <your tenant>.

Step 7: Create a Client Secret

  1. Under Manage, select Certificates & secrets > Client secrets > New client secret.
  2. Enter the description workshop-<date> and choose the shortest expiration that covers the workshop, or set a custom one.
  3. Select Add.
  4. Copy the secret Value immediately and store it safely. It's never shown again after you leave the page.
Important: Copy the Value, not the Secret ID. Never paste the secret into source code, a config file in a repository, chat, or a ticket. You read it from an environment variable in Labs 05 and 06.
Note: Client secrets are for development and workshops. Production daemons should use a certificate, a federated credential, or a managed identity. See Protect App Credentials.

Test and Verify

On App registrations > All applications, search for graph-workshop and check each app.

  • Both registrations exist and are single tenant.
  • graph-workshop-user-<suffix> has Allow public client flows set to Yes and two delegated permissions.
  • graph-workshop-daemon-<suffix> has only User.Read.All (Application), with status Granted.
  • The daemon has one client secret with an expiration date.
  • You recorded: tenant ID, user app client ID, daemon client ID, and daemon secret value.

Cleanup and References

Keep both registrations until you finish the code labs (Labs 04 to 06). App registrations have no cost, but an unused app with a valid secret and consented application permissions is a security risk. When you finish the workshop:

  1. In App registrations, open graph-workshop-daemon-<suffix> and select Delete, then confirm.
  2. Repeat for graph-workshop-user-<suffix>.
  3. Delete any local copy of the client secret.
