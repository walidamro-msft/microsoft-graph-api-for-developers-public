Authentication and Permissions

How your app proves who it is, what it is allowed to do, and who has to agree to it before Microsoft Graph returns any data.

Microsoft Entra IDConcepts~12 min

Three Things Every Call Needs

Microsoft Graph is a protected API gateway for accessing data in Microsoft cloud services like Microsoft Entra ID and Microsoft 365. It's protected by the Microsoft identity platform, which authorizes and verifies that an app is authorized to call Microsoft Graph.

Source: Authentication and authorization basics, Microsoft Learn

1. An app registration

Makes your app known to the Microsoft identity platform and gives it an Application (client) ID.

2. Permissions with consent

Microsoft Graph permissions such as User.Read, granted by a user or an admin.

3. An access token

Issued by Microsoft Entra ID and sent as Authorization: Bearer <token> on every request.

Learn more: Authentication and authorization basics

App Registration

You register the app once in the Microsoft Entra admin center under Entra ID > App registrations. No code is uploaded; you only describe the app to the identity platform. Registration requires at least the Application Developer role.

SettingWhat it is
Application (client) IDUnique ID that your code sends when it asks for a token.
Directory (tenant) IDThe Microsoft Entra tenant the app is registered in.
Supported account typesWho can sign in: your tenant only (recommended for most apps), any Microsoft Entra tenant, and optionally personal Microsoft accounts.
Redirect URIWhere the identity platform returns tokens for interactive sign-in. Not needed for device code or app-only flows.
CredentialA certificate, a federated identity credential, or a client secret. Only confidential clients have one.

Public client

Desktop, mobile, CLI, and single-page apps. The code runs on a device where a secret can't be protected, so the app has no credential and can only act on behalf of a signed-in user.

Confidential client

Web apps, web APIs, and background services that run on a server. They hold a credential and can act on behalf of a user or as themselves.

Delegated and App-Only Access

An app calls Microsoft Graph in one of two ways. The access scenario decides which permission type you request and how the token is issued.

Purple band: a user is present. Blue band: the app acts with its own identity.

Delegated access

The app acts on behalf of a signed-in user. Both the app and the user must be authorized: the app can never access anything the user can't.

App-only access

The app acts with its own identity, for example a nightly sync or a backup daemon. It can access any data its application permissions cover across the tenant.

Permission names follow the pattern {resource}.{operation}.{constraint}. When the constraint is missing, access is limited to the signed-in user's own data.

PermissionAllows the app to
User.ReadRead the signed-in user's profile
User.ReadBasic.AllRead basic profile properties of all users
User.Read.AllRead full profiles of all users
Group.CreateCreate groups, but not modify or delete them
Application.ReadWrite.OwnedByManage only the apps it created or owns
Note: The same name can exist as both types. User.Read.All as a delegated permission is limited by the user's access; as an application permission it reads every user in the tenant.

Consent

A permission does nothing until someone consents to it. Consent is recorded in the tenant, so it's a governance decision, not just a developer setting.

  • User consent works for low-impact delegated permissions such as User.Read or User.ReadBasic.All, when your tenant's app consent policy allows it.
  • Admin consent is required for higher-impact delegated permissions such as User.Read.All, and for every application permission.
  • Only a Privileged Role Administrator or Global Administrator can consent to application permissions.
  • In the portal, admins select API permissions > Grant admin consent for <tenant> on the app registration.
Note: App-only apps request the special scope https://graph.microsoft.com/.default. It means "all application permissions already configured and consented on this app registration", so you add them in the portal first.

Access Tokens

The app attaches the token to every request in the Authorization header. Microsoft Graph validates the token and its claims, which include the app's permissions and, for delegated access, the user.

HTTP request 
GET https://graph.microsoft.com/v1.0/me HTTP/1.1
Host: graph.microsoft.com
Authorization: Bearer <access-token>

Don't build token requests by hand. Use an authentication library that handles caching, refresh, and protocol details for you:

Azure Identity

Credential classes such as DeviceCodeCredential, InteractiveBrowserCredential, and ClientSecretCredential. The Microsoft Graph SDKs accept these directly.

MSAL

The Microsoft Authentication Library for .NET, Java, Python, JavaScript, and mobile platforms. Azure Identity uses it internally.

Important: Treat an access token like a password while it's valid. Don't paste tokens into chat, tickets, or shared tools.
Learn more: Access tokens

Key takeaway

Use delegated permissions whenever a user is present; app-only access is the most privileged option. Request the smallest permission that does the job, and remember that application permissions always need an admin.
