Making Requests

Read and write Microsoft Graph data with plain HTTP: the request shape, query parameters that shrink responses, and paging through large collections.

REST and ODataConcepts~10 min

Anatomy of a Request

{HTTP method} https://graph.microsoft.com/{version}/{resource}?{query-parameters}
PartExamplePurpose
MethodGETWhat you want to do with the resource
Versionv1.0Generally available or preview APIs
Resourceusers/{id}/memberOfThe entity, collection, or relationship you address
Query parameters$select=displayNameShape, filter, sort, and page the response
HeadersAuthorization, ConsistencyLevelToken and request options

Every response carries an HTTP status code, an optional JSON body, an @odata.nextLink when more pages exist, and response headers including request-id. Keep the request-id: it's what Microsoft support asks for.

HTTP Methods

MethodDoesBody
GETRead data from a resourceNone
POSTCreate a resource or perform an action, such as /me/sendMailJSON
PATCHUpdate a resource with new values, or upsert itJSON with only the changed properties
PUTReplace a resource with a new oneJSON or content
DELETERemove a resourceNone
Note: Use PATCH, not PUT, to update most Microsoft Graph resources. PUT replaces the whole resource and is used by a smaller set of APIs, such as uploading file content.
Important: Write requests are limited to 4 MB, and some APIs are lower. Larger requests fail with 413 Request Entity Too Large; use the upload session APIs for large files.

Create, Update, and Delete

Write requests send JSON with a Content-Type: application/json header. Successful writes often return no body, so check the status code.

POST: create a security group (201 Created, returns the group) 
POST https://graph.microsoft.com/v1.0/groups
Content-Type: application/json

{
  "displayName": "Graph Workshop",
  "mailEnabled": false,
  "mailNickname": "graph-workshop",
  "securityEnabled": true
}
PATCH: update your own profile (204 No Content) 
PATCH https://graph.microsoft.com/v1.0/me
Content-Type: application/json

{
  "officeLocation": "18/2111"
}
DELETE: remove the group (204 No Content) 
DELETE https://graph.microsoft.com/v1.0/groups/{group-id}

Send only what changes

A PATCH body contains only the properties you update. Everything else keeps its value.

Writes need more permission

Creating a group needs Group.ReadWrite.All (delegated) or Group.Create (application); reading needs less. Each API reference page lists the least-privileged option.

Deletes can be soft

Deleted Microsoft 365 and security groups can be restored for 30 days.

Call the API Directly

Microsoft Graph is plain HTTPS, so any HTTP client works: curl, HttpClient, requests, or Invoke-RestMethod. Add the token in the Authorization header and read the JSON that comes back.

Bash 
curl -s "https://graph.microsoft.com/v1.0/me?\$select=displayName,mail" \
  -H "Authorization: Bearer $TOKEN"
PowerShell 
$headers = @{ Authorization = "Bearer $env:TOKEN" }
Invoke-RestMethod -Uri 'https://graph.microsoft.com/v1.0/me?$select=displayName,mail' -Headers $headers

Good for

  • Understanding exactly what goes over the wire.
  • Languages without a Microsoft Graph SDK.
  • A single call where an SDK is too heavy.

You handle it yourself

  • Getting and refreshing tokens (use MSAL or Azure Identity).
  • Retrying 429 and 503 responses.
  • Following @odata.nextLink.
Important: For quick tests you can copy a token from Graph Explorer's Access token tab. Keep it in an environment variable, never in a script or a shared file, and let it expire.

The Microsoft Graph SDKs do the token, retry, and paging work for you, which is why the code labs use them.

Query Parameters

OData system query options shape GET responses. Support varies by API and version, so check the Optional query parameters section of each API reference page. Always include the $ prefix.

ParameterDoesExample
$selectReturns only the properties you list/users?$select=displayName,mail
$filterReturns only matching items/users?$filter=startswith(displayName,'A')
$topSets the page size/users?$top=5
$orderbySorts results/users?$orderby=displayName
$expandIncludes a related resource/me?$expand=manager
$countAdds the total count/me/messages?$count=true
$searchMatches a search expression/me/messages?$search="pizza"
Tip: Always use $select. It reduces payload size and improves performance, and for directory objects such as users and groups, v1.0 returns only a default subset of properties unless you ask for others with $select.
Note: Unsupported query parameters sometimes fail silently. If a result looks unfiltered, check the API reference before you trust it.
Learn more: Use query parameters to customize responses

Filter on the Server for Performance

Every item and property you download and then throw away costs network time, memory, and throttling quota. Let Microsoft Graph do the filtering: ask for fewer rows with $filter, fewer columns with $select, and bigger pages with $top where the API allows it.

flowchart LR
    ALL[(Whole collection)] --> F["$filter: fewer rows"]
    F --> S["$select: fewer properties"]
    S --> T["$top: page size"]
    T --> APP([Small response])
    class ALL data
    class F,S,T azure
    class APP success

Each step shrinks the response before it leaves Microsoft Graph.

Avoid: download every user, page by page, then discard most of them in code 
GET https://graph.microsoft.com/v1.0/users
Prefer: return only enabled Sales users, with three properties each 
GET https://graph.microsoft.com/v1.0/users?$filter=department eq 'Sales' and accountEnabled eq true&$select=id,displayName,mail

Filter Operators

TypeOperatorsExample
Equalityeq, ne, not, in, has/users?$filter=department in ('Retail', 'Sales')
Relationallt, gt, le, ge/me/messages?$filter=receivedDateTime ge 2026-09-01
Functionsstartswith, endswith, contains/users?$filter=startswith(userPrincipalName, 'admin')
Conditionaland, or/me/messages?$filter=receivedDateTime ge 2026-09-01 and receivedDateTime lt 2026-10-01
Lambda (collections)any/groups?$filter=groupTypes/any(c:c eq 'Unified')

Check support first

The property table on each resource reference page lists which $filter operators each property supports. Unsupported filters can fail, or be ignored without an error.

Advanced queries

On users, groups, and other directory objects, ne, not, endswith, and filtering on collection counts need ConsistencyLevel: eventual and $count=true. See Advanced Queries.

Syntax details

  • Quote strings: 'Sales'.
  • Don't quote GUIDs or DateTimeOffset values.
  • all isn't supported; negate any with not.
Performance habitWhy it helps
Always $select the properties you useSmaller payloads. For Microsoft Entra objects, $select also lowers the request's throttling cost by 1 resource unit.
Use $filter instead of reading everythingFewer pages, fewer calls, less data to process.
Use $expand only when you need the related dataFor Microsoft Entra objects, $expand raises the request's throttling cost by 1 resource unit.
Add $count=true only when you need the totalOn directory objects, $count needs advanced query parameters, which return eventually consistent results.
Use delta queries for repeated readsAfter the first full read, you get only what changed.
Note: Items that reference properties your app isn't allowed to read are left out of filtered results. If a filter returns fewer items than you expect, check permissions as well as the expression.

Advanced Queries on Directory Objects

Users, groups, applications, devices, and other Microsoft Entra objects support extra query capabilities that run against a separate index. You turn them on with two advanced query parameters:

  • The request header ConsistencyLevel: eventual
  • The query string $count=true (not needed for $search)
Disabled accounts, using the ne operator 
GET https://graph.microsoft.com/v1.0/users?$filter=accountEnabled ne true&$count=true&$select=displayName
ConsistencyLevel: eventual

Needs advanced query parameters

  • ne and not operators
  • endsWith on mail or userPrincipalName
  • $search on directory objects
  • $filter and $orderby together
  • /users/$count

Watch out

  • $expand isn't supported in advanced queries.
  • Results are eventually consistent: new objects can take a moment to appear.
  • The header isn't copied to the next page automatically.
Learn more: Advanced query capabilities on Microsoft Entra ID objects

Paging

Collections come back one page at a time. GET /users returns 100 users per page by default; $top sets a different page size where the API allows it. When more data exists, the response includes @odata.nextLink.

flowchart LR
    REQ[GET /users?$top=5] --> PAGE[Process page]
    PAGE --> Q{nextLink present?}
    Q -->|Yes| NEXT[GET the full nextLink URL]
    NEXT --> PAGE
    Q -->|No| DONE([All results read])
    class REQ azure
    class PAGE data
    class Q neutral
    class NEXT warning
    class DONE success

Keep requesting the full @odata.nextLink URL until it no longer appears.

  • Use the entire @odata.nextLink URL. Don't extract $skiptoken and build your own URL.
  • A page can contain zero items and still have a next link.
  • Custom headers such as ConsistencyLevel must be added again to each page request.
  • The SDKs include a PageIterator that follows next links for you.
Learn more: Paging Microsoft Graph data in your app · Page through a collection with the SDKs

Tools for Trying Requests

Graph Explorer

Web tool at aka.ms/ge. Run queries against sample data or your tenant, find permissions, and copy SDK code. See Graph Explorer.

Microsoft Graph PowerShell

Invoke-MgGraphRequest sends any REST call with the PowerShell session's token, useful for APIs that don't have a cmdlet yet.

Postman

Use the Microsoft Graph Postman collection to save and share requests.

Important: Write requests in Graph Explorer change real data in the tenant you sign in to. Use a developer or test tenant.

Key takeaway

Use v1.0, filter and $select on the server so you only receive what you need, add ConsistencyLevel: eventual and $count=true for advanced directory queries, and always follow @odata.nextLink.
